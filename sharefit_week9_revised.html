Swimlane Diagram

운동 완료 요청이 처리되는 전체 과정

Flutter
1 · 요청 전송 workoutId와 러닝인 경우 distanceM을 서버로 전송
Controller
2 · API 입구 @PatchMapping("/{workoutId}/complete")로 요청을 받고 Service 호출
Request DTO

Service
4 · 핵심 로직 운동 조회 → 소유자 확인 → 완료 가능 상태 확인 → 러닝이면 거리 검증 → 완료 처리
Repository
5 · 데이터 조회 PESSIMISTIC_WRITE로 같은 운동 행을 잠그고 필요한 Entity를 조회
Entity + JPA
6 · 상태 변경 workout.complete() 실행 → status / endedAt / durationSeconds 변경
DB
7 · COMMIT JPA Dirty Checking으로 UPDATE 수행 · 러닝이면 거리 및 단순화 경로도 함께 저장
Response DTO
8 · 응답 반환 workoutId / status / endedAt / durationSeconds를 JSON으로 Flutter에 반환

WorkoutController.java

① API 요청을 받는 부분

WorkoutController.java
// 운동 완료 API
@PatchMapping("/{workoutId}/complete")
public WorkoutCompleteResponse completeWorkout(
        // URL의 workoutId를 받음
        @PathVariable Long workoutId,

        // 러닝이면 Body에 distanceM이 들어오고,
        // 헬스면 Body가 없어도 되므로 required = false
        @RequestBody(required = false)
        WorkoutCompleteRequest request
) {
    // Controller에서는 직접 DB 처리를 하지 않고
    // Service에 필요한 값만 넘김
    return workoutService.completeWorkout(
            workoutId,
            currentUserId(),
            request
    );
}

Controller 역할

  • URL과 HTTP Method 연결
  • PathVariable 수신
  • Request Body 수신
  • 현재 사용자 ID 전달
  • 실제 비즈니스 로직은 Service에 위임

06 · Service
WorkoutService.java

③ 운동 완료의 핵심 로직

WorkoutService.java
@Transactional
public WorkoutCompleteResponse completeWorkout(
        Long workoutId,
        Long currentUserId,
        WorkoutCompleteRequest request
) {
    // 1. 운동을 조회하면서 해당 행을 잠금
    Workout workout = workoutRepository
            .findByIdForUpdate(workoutId)
            .orElseThrow(() ->
                    new NotFoundException("운동 기록이 없습니다."));

    // 2. 현재 사용자의 운동인지 확인
    checkOwner(workout, currentUserId);

    // 3. 이미 완료된 운동인지 등 상태 확인
    validateCompletable(workout);

    RunningDetails details = null;

    if (workout.isRunning()) {
        // 4. 러닝이면 distanceM 필수
        BigDecimal distance = validateDistance(request);

        // 5. 러닝 상세 정보 조회
        details = runningDetailsRepository
                .findById(workoutId)
                .orElseThrow(() ->
                        new NotFoundException("러닝 상세가 없습니다."));

        // 6. 최종 거리 저장
        details.updateDistance(distance);
    }

    // 7. status / endedAt / durationSeconds 변경
    workout.complete(LocalDateTime.now(workoutClock));

    if (details != null) {
        // 8. 저장된 GPS 경로를 RDP 2.5m로 단순화
        simplifyRoute(workoutId);
    }

    // 9. 완료된 운동 정보를 Response DTO로 변환
    return WorkoutCompleteResponse.from(workout);
}

Service가 담당하는 것

  • 존재 여부 확인
  • 사용자 권한 확인
  • 완료 가능한 상태인지 확인
  • 러닝 거리 검증
  • 운동 완료 처리
  • RDP 경로 단순화
@Transactional로 묶여 있으므로 중간에 예외가 발생하면 전체 작업을 ROLLBACK합니다.
07 · Repository
WorkoutRepository.java

④ DB에서 운동 데이터를 조회하는 부분

WorkoutRepository.java
public interface WorkoutRepository
        extends JpaRepository<Workout, Long> {

    // 같은 운동을 동시에 완료하려는 상황 방지
    @Lock(LockModeType.PESSIMISTIC_WRITE)

    // workoutId에 해당하는 운동을 조회
    @Query("""
        select w
        from Workout w
        where w.workoutId = :workoutId
    """)
    Optional<Workout> findByIdForUpdate(
            @Param("workoutId") Long workoutId
    );
}

PESSIMISTIC_WRITE

조회한 운동 행에 DB Lock을 걸어 다른 트랜잭션이 동시에 수정하지 못하도록 합니다.

  • 중복 완료 방지
  • 동시에 상태가 변경되는 문제 방지
  • 한 트랜잭션이 끝난 뒤 다음 수정 허용
08 · Entity
Workout.java

⑤ 실제 운동 상태를 바꾸는 부분

Workout.java
@Entity
@Table(name = "workouts")
public class Workout {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long workoutId;

    // IN_PROGRESS → COMPLETED 로 변경
    @Enumerated(EnumType.STRING)
    private WorkoutStatus status;

    private LocalDateTime startedAt;
    private LocalDateTime endedAt;
    private Long durationSeconds;

    public void complete(LocalDateTime now) {
        // 1. 종료 시간 저장
        this.endedAt = now;

        // 2. 실제 운동 시간 계산
        // 필요 시 일시정지 시간은 별도 계산 로직에서 제외
        this.durationSeconds =
                Duration.between(this.startedAt, now)
                        .getSeconds();

        // 3. 최종 상태를 완료로 변경
        this.status = WorkoutStatus.COMPLETED;
    }

    public boolean isRunning() {
        return this.type == WorkoutType.RUNNING;
    }
}

Entity에서 바뀌는 값

  • status → COMPLETED
  • endedAt → 현재 종료 시간
  • durationSeconds → 실제 운동 시간
Entity는 트랜잭션 안에서 조회된 상태이므로 값만 바꿔도 JPA가 변경을 감지합니다.

public record WorkoutCompleteResponse(
        Long workoutId,
        String status,
        LocalDateTime endedAt,
        Long durationSeconds
) {

    public static WorkoutCompleteResponse from(
            Workout workout
    ) {
        // Entity 전체를 보내지 않고

        return new WorkoutCompleteResponse(

}

11 · RDP 적용 이유
러닝 GPS 경로

GPS 좌표를 왜 줄였는가?

문제

러닝 중 GPS 좌표가 계속 쌓이면 저장량과 조회 데이터가 커집니다.

3,924개

첫 번째 공개 GPX 원본 좌표

RDP 방식

경로의 전체 형태를 최대한 유지하면서 불필요한 중간 좌표를 제거합니다.

epsilon = 두 유지점 사이 직선에서 중간 좌표가 벗어날 수 있는 허용 거리

공개 러닝 GPX를 먼저 약 5m 간격으로 공간 샘플링한 뒤, RDP 1m / 2m / 2.5m / 3m / 5m를 각각 비교했습니다.

14 · 결론 / 다음 주
9주차 마무리

현재 RDP epsilon 후보: 2.5m

2.5m를 선택한 이유

  • 1m: 형태는 잘 유지되지만 좌표 감소 효과가 상대적으로 낮음
  • 2m: 안정적이지만 2.5m보다 좌표가 더 많이 남음
  • 2.5m: 2m와 형태 차이는 거의 없고 좌표는 더 감소
  • 3m 이상: 곡선이 많은 코스에서 단순화가 보이기 시작
  • 5m: 트랙 곡선 형태 변화가 큼

실제 ShareFit 사용자 GPS 데이터가 확보되면 다시 조정할 수 있습니다.
